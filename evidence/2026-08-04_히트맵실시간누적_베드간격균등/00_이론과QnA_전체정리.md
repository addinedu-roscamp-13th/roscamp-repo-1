# 히트맵 실시간 누적 · 베드 간격 균등 (2026-08-04)

## 1. 문제 — 순찰 도중 앞서 찍은 구역이 사라진다

베드 3개 × 구역 4개 = **12개 촬영점**. 어제(8/3) 시험에서 베드1의 2번째를 찍다가
베드2로 넘어가면 베드1 내용이 초기화되는 것처럼 보였다.

### 원인: ACS 는 기억하지 않는다

보연님 `detection_service.py` 주석에 명시돼 있다.

```
"""순찰 현황 중계(notify) 몸통. zone_cumulative 는 없음(제거됨)."""
```

notify 가 보내는 것은 **지금 이 지점의 스냅샷 하나**뿐이다.

```
task_id, waypoint_id, robot_id, detection_id,
ripe_percent, unripe_percent, rotten_percent, disease_percent, detected_at
```

앞서 찍은 지점은 실려오지 않는다. **누적은 웹서비스 쪽 몫**이다.

## 2. 요구 — 히트맵과 작물 %를 분리한다

| | 언제 표시 | 이유 |
|---|---|---|
| 히트맵 점 | **찍는 즉시** (누적) | 지도는 '어디까지 훑었나'를 보여주는 것이라 진행 중에도 늘어나야 쓸모가 있다 |
| 작물 상태 % | **순찰 완료 후** | 농장 전체를 대표하는 수치라, 절반만 돈 평균을 보여주면 그게 최종값인 줄 알고 판단하게 된다 |

## 3. 구현 (`services/automato_web_service/app.py`)

### `_apply_detection_to_heat(d)` — 검출 1건 도착
- `by_waypoint[wp]` 에 **즉시** 기록 → 히트맵에 점이 하나 늘어난다
- `pending.waypoints[wp]` 에도 쌓는다 → 완료 시 평균 낼 재료
- `task_id` 가 바뀌면 새 순찰 → `by_waypoint`·`pending`·`crop_ready` 모두 초기화
- `heat.json` 에 쓰므로 **서버를 재시작해도 남는다**

### `_commit_heat_on_patrol_completed(d)` — 완료 신호
- `pending` 의 방문 지점 **평균**으로 `crop` 확정, `crop_ready = True`
- 히트맵은 이미 채워져 있으므로 놓친 지점만 메운다
- `pending.task_id` 는 남긴다 → 완료 직후 지각 도착한 검출이 '새 순찰'로 오인돼 지도를 지우는 것을 막는다

### `GET /api/heatmap` — 게이트
- `source != "acs"` → 전부 null (`awaiting_patrol`)
- `crop_ready` 아님 → **`crop` 만 null** (`crop_pending`), `by_waypoint` 는 그대로 내보낸다

> ⚠ **여기가 함정이었다.** 첫 검출이 오는 순간 `source="acs"` 가 되는데,
> `crop_ready` 게이트가 없으면 **시드값(익음 34.2% / 병해충 4.7%)이 그대로 새어나가**
> 순찰 도중에 가짜 '병해충 4.7%' 경보가 뜬다. (7/30 통합시험에서 겪은 것과 같은 유형)

## 4. 구현 (`client/farm_admin_app/index.html`)

- 히트맵 폴링 **5초 → 2초** (검출이 서버에 즉시 반영되므로 이 폴링이 실시간 통로)
- 히트맵 부제 / 작물 카드에 `순찰 중 · N/12 구역 촬영 완료` 표시
- 작물 카드가 **'대기'(순찰 시작 전)** 와 **'진행 중'** 을 구분

## 5. 베드 간격 균등화

### 이전
```
좌벽 │ 3.92 │ 베드2(2.10) │ 2.00 │ 베드3(1.90) │ 3.08 │ 우벽     ← 가운데만 좁음
```

### 맞바꿈 — 균등 간격 vs 주행 여유

통로가 균등하면 `3g + 베드폭합 = 13.00` 이 강제된다.
베드를 두껍게 할수록 통로 `g` 가 줄고, 왼쪽 통로 촬영점(WP12 x=-3.63)에 선
Pinky(폭 0.95)가 베드2를 파고든다.

| 통로 g | 베드2 | 베드3 | 현재대비 | WP12 겹침 |
|---|---|---|---|---|
| 3.345 | 1.56 | 1.41 | 26% 얇음 | 없음 |
| **3.20** | **1.79** | **1.62** | **15% 얇음** | **0.15 m** ← 채택 |
| 3.00 | 2.10 | 1.90 | 그대로 | 0.35 m |

0.15 는 로봇 폭 0.95 중 일부라 화면에서 거의 드러나지 않고, 베드도 26%까지
얇아지지 않아 빈약해 보이지 않는다. **그 절충점.** (이건수 판단: "적당히 얇게")

### 채택
```
좌벽 │ 3.20 │ 베드2(1.79) │ 3.20 │ 베드3(1.62) │ 3.20 │ 우벽
베드2 중심 x = -2.41   베드3 중심 x = 2.49
```

`map_layout.py` 가 **"구조물은 배치·비율만 참고, 노드·통로만 진짜"** 라 명시 → 폭 조정 허용.

## 6. 촬영점의 소속 베드를 못박았다

전에는 '가장 가까운 베드'로 추정했는데 **두 가지가 깨졌다.**

1. **짝 노드(10↔18, 13↔19)는 원리상 구분 불가.** 같은 자리에서 방향만 돌려
   반대쪽 베드를 찍으므로 물리 좌표가 같다. 거리로는 절대 갈라낼 수 없다.
2. **베드를 조금만 옮겨도 소속이 바뀐다.** 이번 균등화 때 실제로 WP13 이
   베드2→베드3 으로 넘어가 4/4/4 가 3/5 로 깨졌다.

→ `waypoints[].bed` 로 명시. 어느 베드를 향해 찍는지는 **측정으로 정해진 사실**이지
좌표에서 유추할 것이 아니다.

```
베드1(bed:0)  WP 1, 2, 5, 6
베드2(bed:1)  WP 9, 12, 13, 18
베드3(bed:2)  WP 10, 11, 14, 19
```

`hx` = 히트맵 그리기 전용 x. 짝 노드가 한 점으로 겹쳐 보이지 않게 각자 바라보는
베드 쪽으로 밀어 그린다. **실좌표 `x` 는 손대지 않는다** (로봇 위치 변환에 계속 쓰임).

## 7. 검증 (작업서버 7400)

```
1차 순찰
  12곳 촬영     히트맵 12점 | 작물 감춤       ← 도중엔 % 안 나옴
  완료          히트맵 12점 | 익음 31.6%      ← 12곳 평균으로 확정
2차 순찰
  1곳 촬영      히트맵  1점 | 작물 감춤       ← 새 순찰이면 지도·%  모두 초기화
  2곳 촬영      히트맵  2점 | 작물 감춤
  완료          히트맵  2점 | 익음 11.0%
```

- 순찰 중단 시: 찍은 만큼은 지도에 **남는다** (예전엔 완료돼야만 떠서 전부 유실)
- 완료 후 지각 검출: 지도를 **안 지운다** (3점 → 4점)
- 화면 확인: 히트맵 `순찰 중 · 7/12 구역 촬영 완료` → 완료 후 베드1/2/3 = 29%/34%/31%,
  작물 익음 32.7% · 안익음 62.1% · 병충해 5.2%

## 8. 겪은 사고 — pkill 자기매칭 (2회)

`pkill -f "PORT=7400"` 과 `"app.py" in cmdline` 둘 다 **셸 자신의 명령줄**에
그 문자열이 들어있어 스스로를 죽였다(exit 144).

**교훈:** 명령줄 전체 매칭 대신 `cmdline == ["python3","app.py"]` 처럼 **정확히** 비교하고
자기 PID·부모 PID를 제외할 것. 포트 점유 프로세스는 `/proc/net/tcp` 의 inode 역추적이 확실하다.

# 2차 수정 (같은 날 오후) — 배치 정리 · ACS 평균 수신

## 10. 히트맵 12개를 격자로 정렬

실좌표(로봇이 통로에서 멈춘 자리) 그대로 그리니 12개가 제각각 흩어져 지저분했다.

실제 촬영은 **베드 한 면당 2곳**이다. 그래서 베드마다
**양면 2줄 × 길이 1/4·3/4 지점 = 2×2 격자**에 맞춰 그린다.
배치의 뜻(어느 베드의 어느 구간)은 그대로면서 화면만 반듯해진다.

| 베드 | 촬영줄 | 길이방향 위치 |
|---|---|---|
| 베드1(가로) | z = -9.30 / -5.40 | x = -4.25 / -0.41 |
| 베드2(세로) | x = -3.86 / -0.97 | z = -1.26 / 2.40 |
| 베드3(세로) | x = 1.13 / 3.85 | z = -1.26 / 2.40 |

`waypoints[].hx / .hz` = **그리기 전용 좌표**. 실좌표 `x·z` 는 손대지 않는다
(로봇 위치 변환·베드 밀집도 계산에 계속 쓰인다).
짝 노드(10↔18, 13↔19)가 한 점으로 겹치던 것도 이걸로 함께 해결됐다.

## 11. DG 충전 스테이션 — 로봇이 주차칸 앞에 서 보이던 문제

**증상:** dg_03 이 실제로 주차를 마쳐도 GUI 에서는 칸 앞에 나와 있었다.

**원인:** 로봇의 3D 위치는 `_map_to_norm` 으로 변환한 **실측 좌표**로 찍히는데,
파킹 박스는 눈대중으로 뒤쪽 벽(z≈12.03)에 붙여놨었다.
도킹 노드(22·23·24)는 z = 6.80 / 7.56 / 7.45 → **4.5~5.2m 어긋남.**

보연님 `map_layout.py` 도 시설 박스를 "노드 기준 고정된 행"에 그린다고 명시한다.

**조치:** `z = 7.50` 으로 옮김. 박스(깊이 1.95)가 6.53~8.48 을 덮어
**세 도킹 노드가 모두 칸 안에 들어온다.**

**x 는 균등·밀착:** 실측 노드 간격이 2.60 / 1.90 이라 DG1 만 떨어져 보였다.
간격 1.90(박스폭 1.82 → 틈 0.08)으로 붙이고 노드 오차를 0.35 로 균등 분배.
→ `x = -3.94 / -2.04 / -0.14`

> ⚠ **더 왼쪽 벽(x=-6.50)까지 밀지 않았다.** 벽에 붙이려면 노드에서 1.3m 이상
> 멀어져 방금 고친 '로봇이 칸 밖에 서 보이는' 문제가 그대로 되살아난다.
> 벽까지 1.50 남긴 것이 두 요구를 함께 만족시키는 한계다.

**같은 문제가 예냉실에도 있다** — 박스 z=12.10 인데 진입 노드 25 는 z=5.28.
이번엔 건드리지 않았다(요청 범위 밖).

## 12. 작물 % — ACS 가 보내는 전체 평균을 우선 사용

보연님이 순찰 완료 시 **평균값을 한 번에** 보내주기로 했다(이건수 확인).

`_commit_heat_on_patrol_completed` 가 두 갈래로 동작한다.
1. 완료 콜백에 `ripe_percent / unripe_percent / rotten_percent / disease_percent`
   가 실려오면 **그대로 사용** (`summary` 안에 있어도 읽는다)
2. 없으면 이쪽 `pending` 을 방문 지점 평균으로 (폴백)

ACS 값을 우선하는 이유: 순찰 도중 검출 콜백이 몇 건 유실되면 이쪽 평균은 그만큼
치우친다. ACS 가 낸 전체 평균이 더 정확하다.

**검증:** 12곳 검출 후 완료에 `ripe 36.4 / disease 5.7` 을 실어 보냄
→ 화면 `익음 36.4% · 병해충 5.7%`, 로그 `작물 상태 확정(ACS 평균)` ✓

## 14. 충전소 — 세 번 바꾼 끝에 내린 결론

**결론(이건수 결정): 배치는 벽 기준으로, 로봇은 실좌표 그대로. 칸 앞에 서 보이는 것은 감수한다.**

```
z = 11.91 → 박스 바깥 끝 12.88 (벽 13.00 안쪽 0.12)
x = -5.47 / -3.57 / -1.67 → DG1 이 위쪽 벽(-6.50) 안쪽 0.12, 칸 사이 틈 0.08 균일
```

### 왜 셋 다 만족시킬 수 없었나

로봇 위치는 `_map_to_norm` 변환 **실측 좌표**라 언제나 진짜다.
그런데 도킹 노드(22·23·24)는 z = 6.80 / 7.56 / 7.45 로, 벽(13)에서 **5.4~6.2 안쪽**이다.
즉 **충전소는 실제로 벽에 붙어 있지 않다.** 그래서 셋을 동시에 만족시킬 수 없다.

| 시도 | 벽 밀착 | 로봇이 칸 안 | 박스 크기 | 결과 |
|---|---|---|---|---|
| ① 벽에 붙임 (원래) | ✓ | ✗ (5m 앞) | 실물 | 칸 앞에 서 보임 |
| ② 도킹 노드로 내림 | ✗ (5.5 뜸) | ✓ | 실물 | 허공에 뜬 것처럼 보임 |
| ③ 벽~노드 슬롯 (깊이 6.65) | ✓ | ✓ | **6.65** | **화면이 거짓말** |
| **④ 벽에 붙임 + 간격 균일** | ✓ | ✗ | 실물 | **채택** |

### ③을 되돌린 이유 — 중요

박스를 6.65 로 늘리면 로봇이 그 구간 **어디에 서든** 주차한 것처럼 보인다.
정차 좌표를 모른다는 **내 불확실성을 박스를 키워 덮은 것**이고, 엉뚱한 데 선 로봇까지
'주차 완료' 로 보이게 만든다.

> 이건수 지적: "실제 주차장 안에 주차한거여야 그렇게 떠야하는거야.
> 다른 곳에 주차했으면 다른 곳 그 위치가 정확히 GUI에 표현되어야해"

**표시를 편하게 하려고 정확도를 희생하면 안 된다.** ④는 배치가 실제와 다른 것을
**알고 감수**하는 것이지, 로봇 위치를 왜곡하는 것이 아니다. 로봇은 언제나 실좌표에 찍힌다.

### 정확히 맞추려면
dg_03 을 충전소에 보내 **도킹 완료 시점의 `map_position` 을 실측**해 그 자리에 박스를 놓으면 된다.
(노드 22·23·24 는 '진입' 지점이라 도킹 완료 자리와 다를 수 있다. 아직 실측 못 했다.)

### 알아낸 것 — 그려진 '벽' 은 온실 벽이 아니다

`/api/telemetry` 의 map: `width_m 1.17 · height_m 1.92 · origin (-0.193,-0.632)`
→ 실측 노드 전체가 씬 좌표로 **x -4.28~4.50, z -10.19~7.56**.
그런데 그리는 경계는 x ±6.5, z ±13 이다.

**+z 쪽 5.44 는 노드가 하나도 없는 빈 맵**이다. PGM 이 온실 바깥 여백까지 포함하기 때문.
시설을 z≈12 에 놓으면 '벽에 붙은' 듯 보이지만 실제로는 온실 밖이고 로봇은 거기까지 안 간다.

> 시설이 '허공에 뜬 것처럼' 보이던 근본 원인이 이것이다.
> 근본 해결은 경계를 실제 온실 범위로 줄이는 것인데 맵 구도가 통째로 바뀌어 보류했다.
> **예냉실(박스 z=12.10 / 진입노드 25 는 z=5.28)도 같은 문제가 남아 있다.**
